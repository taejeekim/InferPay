A buyer agent that pays only for answers it needs and can check

An agent with a budget can waste it two ways: it can pay for an answer it already knows, and it can pay for an answer it cannot check. InferPay is a command-line buyer agent that prices each purchase against its own confidence before any NEAR moves, and shows the arithmetic.

Before it buys, the buyer names the keys from the specialist's catalog that a right answer needs. The specialist must open each of those keys with evidence. The buyer recomputes each check against a hash of the specialist's dataset that the specialist published on NEAR testnet, grades the answer from what it verified and what the specialist withheld, and writes the rating on chain, where it becomes the specialist's reputation for the next decision.

Shops

Each shop publishes only a hash of its private dataset: the Merkle root, the number of entries, and the scheme. Reputation is computed here from the buyer bots' on-chain ratings, the same way the CLI computes it before it decides.

Buyer bots

Each bot has its own account, key, and balance, and a payment is signed only with the key of the bot that asked. A native NEAR transfer cannot draw on another account, so a bot's balance is the most it can spend.

Latest ratings

Each rating is written by a buyer bot under its own account in the SocialDB contract v1.social08.testnet. Newest first, ordered by the block that wrote the rating. Verified counts the checks that opened a key the buyer needed, and withheld counts the needed keys the shop did not open.

The keys the buyer needed

Before the job opens, the buyer names the keys from the shop's catalog that a right answer needs, and the shop must open each one. A needed key the shop does not open is withheld and costs 2 stars, more than a wrong value costs, so for any number of needed keys hiding an entry rates lower than showing it. Any honest delivery rates at least 2, above a forgery. A check on a key the buyer did not ask for counts neither for nor against the shop.

Confidence, coverage, and the needed keys come from the buyer's model call in a real run; here you set them. The buyer may name only keys the shop lists in its catalog, and the CLI drops any other key it names. A shop with no needed key counts as coverage 0, whatever the coverage field says. If the buyer buys, the shop must open every needed key. Reputation with no ratings is the prior, 0.70, which counts as two ratings. A shop accepts any counter-offer at or above its floor.

What is real and what is not

  
Real

  
    
    
  • The buy-or-answer decision, the one counter-offer, the check verification, and the grade run in every mode.
    • 
    
  • The shop delivers first, and the buyer verifies before it pays. It pays nothing if any check is forged, and otherwise the agreed price times the share of needed keys the shop opened to an entry it verified, so a withheld key costs the shop its share. A rating with nothing paid shows nothing paid in the Payment column.
    • 
    
  • The grade counts only the keys the buyer named before the job opened. It starts at 5 and loses 1 per mismatch, 1 per empty slot, 1 per needed key opened with no claim, and 2 per needed key withheld. It is at least 2 unless a check is forged, and 1 if any check is forged.
    • 
    
  • --budget bounds everything the bot spends: prices, gas for each payment and rating, and SocialDB storage for each rating. Before deciding, the buyer reserves an upper bound on the fees and decides with what is left. After the job it measures the fees on chain, and what the reserve did not use goes back to the budget.
    • 
    
  • On the testnet rail, payment is a native NEAR transfer from the buyer bot's own sub-account, and the buyer reads each shop's dataset hash from NEAR testnet before it opens a job.
    • 
    
  • Reputation on the testnet rail comes from ratings that the buyer bots write on NEAR testnet. The 18 accounts are real named accounts on testnet, created through the faucet.
    • 
    
  • With a NEAR AI Cloud key, answers come from NEAR AI Cloud, and each model response is checked against NEAR AI's TEE attestation report.
    • 
  

  
Not real, or not yet

  
    
    
  • Without a NEAR AI key, answers are replayed from 8 recorded questions. Any other question stops before payment.
    • 
    
  • The NEAR Intents rail for mainnet has never run. Every on-chain action shown here is on testnet.
    • 
    
  • The buyer does not read the shop's prose. It prints the shop's sentence as an unverified summary and builds its own answer, one line per needed key, only from the entries it verified, so a summary that misstates an entry changes nothing the buyer relies on.
    • 
    
  • The buyer's model picks the needed keys. Code drops any key that is not in the shop's catalog, but a key the model does not name is never required.
    • 
    
  • A commitment proves consistency, not truth. It shows that a check agrees with the dataset the shop published, not that the dataset is right.
    • 
    
  • The sample datasets and their salts are in the repository, so they are not secret. That is why this page can show a proof.
    • 
    
  • Ratings can be gamed. Anyone can create an account and write a rating. The CLI and this page read only the ratings of the buyer bots under one root.
    • 
    
  • The buyer and the specialists run in one process on one machine.
    • 
    
  • The shop delivers before it is paid, so the shop carries the risk that the buyer never pays. A real deployment would hold the agreed price in an escrow that releases on a verified proof. This demo has none. A shop that fails three times is never paid.
    • 
    
  • The TDX and GPU quotes in the attestation report are not re-verified locally.
    • 
    
  • Two CLI processes paying from the same bot at the same moment can collide on a nonce. The second payment reports uncertain, and resume settles it once the first transaction is found, or, when the first one took its nonce, once its own stored transaction expires, about a day later.
